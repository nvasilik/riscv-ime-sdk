# Developers

For people who change the SDK: its component pins, its build, CI and
releases. To use the SDK or build it from source, see
[README.md](README.md).

## Terms

| Term | Means |
| --- | --- |
| component repo | one of the four source repos: crosstool-NG, gcc, binutils, qemu |
| component image | an image built from component repos: `toolchain` (crosstool-NG, gcc, binutils) or `qemu` |
| SDK image | the image users run, `riscv-ime-sdk`, assembled from the two component images |
| Apptainer image | the `.sif` converted from the SDK image |
| image archive | the SDK image saved as a `.tar.xz` |
| SDK version | `sdk_version` in `components.yaml`, `YYYY.MM.DD`; a release is tagged `openchip-v<version>` |
| pins | the exact commits and base image digest the build uses |

## How pinning works

Two files, as in any package manager: **intent floats, the lock pins**.

- **`components.yaml`** is edited by hand. Each component repo has a
  `ref:`, which may be a moving branch during development.
- **`sdk.lock.yaml`** is generated by `make lock`. It holds the exact
  commit of every component repo, whether its `ref:` named a branch, a
  tag or a commit, and the digest of the `base_image` on Docker Hub.

`make lock` also renders the lock into `build/<stage>/pins.hcl`, one for
each build directory: `toolchain`, `qemu` and `sdk`. **The build reads only
these `pins.hcl` files**, never `components.yaml`. Commit all three
together: `components.yaml`, `sdk.lock.yaml` and `build/*/pins.hcl`.

The lock is the integration gate. Anyone can push to a component repo at
any time, but nothing reaches the SDK until a PR here changes the
component's commit in `sdk.lock.yaml`.

## Maintainer make targets

These are in addition to the targets in
[README.md](README.md#make-targets).

| Target | Does |
| --- | --- |
| `make lock` | resolve `components.yaml` into `sdk.lock.yaml` and render `build/*/pins.hcl` |
| `make pins` | render `build/*/pins.hcl` from the existing lock, without resolving anything |
| `make check` | run the guard checks: no credentials, no internal hosts, no pins outside the lock, and `components.yaml`, lock and pins agree |
| `make check-refs` | check that every tag in `components.yaml` still points at the commit in the lock, and that the base image digest exists |
| `make hashes` | print the component image tags CI looks for |

`make lock` and `make check-refs` additionally need `curl`, access to
Docker Hub and access to the component repos.

`make hashes` uses the git tree hash of `build/toolchain` and `build/qemu`
at `HEAD`, so uncommitted changes are not included.

## Changing a component

To build the SDK from another commit, branch or tag of a component repo:

1. **Land the change in the component repo first.** It must exist
   there as a commit, tag or branch head before this repo can point at
   it.
2. **Point `components.yaml` at it.** Set the component's `ref:` to the
   branch name, tag name or commit SHA:

   ```yaml
   # components.yaml
     gcc:
       repo: https://github.com/<org>/<component-repo>.git
       ref:  deadbeefcafef00d1234567890abcdef12345678   # was: ime-cleanup
   ```

   A moving branch name is fine during development. Once the change is
   settled, pin a tag or an exact SHA, so that `components.yaml` records
   what you meant to build and not whatever was at the branch head that
   day. A release requires it; see [Releasing](#releasing).

   To tag a component commit, see
   [Tagging a component commit](#tagging-a-component-commit).

   Write `refs/heads/<name>` or `refs/tags/<name>` to name a branch or a
   tag explicitly. A bare name that is both a branch and a tag in the
   component repo is an error, so that a branch can never shadow a tag.

3. **Resolve it: `make lock`.** This runs
   [`scripts/make-lock.sh`](scripts/make-lock.sh), which resolves with
   [`scripts/resolve.sh`](scripts/resolve.sh). For each component repo,
   `ref` is a literal 40-character commit SHA, or the branch or the tag
   of that name, peeled to its commit. It writes the result to
   `sdk.lock.yaml` as `commit:`, with `resolved_from: <ref>`,
   `resolved_kind: branch | tag | commit` and a `generated_at`
   timestamp. A `base_image` pinned by digest is checked to exist on
   Docker Hub and kept; a `base_image` tag alone is resolved to its
   current digest. Then it renders `build/<stage>/pins.hcl` for each stage
   listed under `stages:` in `components.yaml`; each holds the base image
   digest and the repo URL and commit of every component repo of that
   stage. It never modifies `components.yaml`.

   `make lock` re-resolves **every** ref, and provides per component information
   with the old and new ref and whether the commit or digest changed. 

   To bump the base image, run `make check-refs`. It reports the digest
   the `ubuntu` tag points at now. Paste it into `base_image` in
   `components.yaml` and run `make lock`. This triggers a rebuild on every image.

4. **Check it: `make check`.** This runs
   [`scripts/check-pins.sh`](scripts/check-pins.sh). It checks that no
   credentials or internal hostnames are in the repo, and that component
   repo URLs appear only in `components.yaml`, `sdk.lock.yaml`,
   `build/*/pins.hcl`, `README.md`, the check script itself and
   `.github/`, never in a Dockerfile or `docker-bake.hcl`. Then it runs
   [`scripts/check-lock.sh`](scripts/check-lock.sh), which checks that
   `components.yaml`, `sdk.lock.yaml` and `build/*/pins.hcl` agree.
   `make check-refs` runs [`scripts/check-refs.sh`](scripts/check-refs.sh),
   which asks the component repos and Docker Hub whether every ref still
   resolves to the lock. The `guard` job of the `sdk` workflow runs all
   three scripts.

5. **Build and test it locally:** `make`, then the checks in
   [Check the build](README.md#check-the-build).

6. **Commit `components.yaml`, `sdk.lock.yaml` and `build/*/pins.hcl`
   together and open a PR.** The diff is small: one `ref:` line, the
   matching `commit:` and `resolved_from:` lines in the lock, and the
   matching `*_COMMIT` line in one `pins.hcl`. That makes it easy to
   review, and easy to find with `git bisect` if the new commit turns
   out to be bad. The `guard` job fails if the `pins.hcl` files
   differ from what the lock renders. All three files are listed in
   [`CODEOWNERS`](.github/CODEOWNERS), so the PR needs approval from a
   named reviewer.

7. **Merge to `main`, then release.** Merging to `main` builds the SDK
   image but does not publish it. A release tag publishes it; see
   [Releasing](#releasing). Until a release is tagged, the new component
   commit is only in `main` and in local builds.

## Repository layout

```text
components.yaml          intent: component repos and refs, SDK version; hand-edited
sdk.lock.yaml            pins: generated by `make lock`, CODEOWNERS-gated
Makefile                 build entry point
docker-bake.hcl          build graph: toolchain, qemu, sdk targets
build/toolchain/         Dockerfile, crosstool-NG defconfig template, pins.hcl
build/qemu/              Dockerfile, pins.hcl
build/sdk/               Dockerfile of the SDK image, Apptainer definition, pins.hcl
scripts/                 make-lock.sh, resolve.sh, check-pins.sh, check-lock.sh, check-refs.sh
.github/workflows/       sdk (pins and lock checks, component and SDK images)
.github/actions/         free-disk, setup-yq
```

## CI

The `sdk` workflow runs four jobs: `guard`, `resolve`, `component` and
`sdk`. `guard` runs the checks of `make check` and `make check-refs` on
every trigger, and the other jobs wait for it, so nothing is built or
pushed from pins it rejects.

### Component images

The toolchain and QEMU are published as separate component images:

```text
ghcr.io/openchip-software/riscv-ime-sdk-toolchain:<hash>
ghcr.io/openchip-software/riscv-ime-sdk-qemu:<hash>
```

`<hash>` is the git tree hash of `build/<component>`. `make hashes`
prints both tags for the current `HEAD`. The `resolve` job computes the
tags and checks which images already exist in GHCR. The `component` job
is a matrix that builds only the missing images.

Every input of a component image lives in its directory: the Dockerfile,
`defconfig.in` for the toolchain, and `pins.hcl`. Any change inside
`build/<component>` gives a new tag and a rebuild. No other change does.
A change to `build/sdk`, the workflows or the README reuses both
component images. A `sdk_version` bump does not rebuild the toolchain,
because the toolchain package version names the gcc commit, not the SDK
version.

Component images are a build cache keyed by their inputs, so every run
from this repo pushes the ones it builds, pull requests included. A
toolchain built on a pull request is reused by `main` after the merge,
and by every other branch with the same inputs. Pull requests from forks
cannot push to GHCR, and component builds for them are not supported.

To force a rebuild with unchanged inputs, bump the number in the
`To force a rebuild` line at the top of `build/<component>/Dockerfile`.
This changes the tree hash.

The component repos are public, so component builds fetch them with no
credentials. The workflows must be able to read
and write the `riscv-ime-sdk-toolchain` and `riscv-ime-sdk-qemu`
packages. If a package is new, link it to this repo and give the repo
write access in the package settings.

### SDK image

The `sdk` job assembles the SDK image from the component images, pinned
by digest, in a few minutes. The image carries the labels
`eu.openchip.ime.toolchain` and `eu.openchip.ime.qemu`, which hold the
component image digests, and a label with the digest of
`sdk.lock.yaml`.

| Trigger | SDK image |
| --- | --- |
| pull request | built, never pushed |
| push to `main` | built, never pushed |
| push of tag `openchip-vYYYY.MM.DD` | pushed as `:openchip-vYYYY.MM.DD`, then `:latest` |
| `workflow_dispatch` with **publish** | pushed as `:openchip-v<short-sha>` |

`<short-sha>` is the first 7 characters of the commit SHA.

The summary of each run lists the component images by digest, whether
each was reused or built in that run, and whether the SDK image was
pushed.

`:latest` is the newest release. Only a release tag moves it. The last
step of the `sdk` job moves it after pushing the release image.
It skips the move if a release tag with a later date exists, so a re-run
of an older release never moves `:latest` back.

Every image carries `sdk_version` from `sdk.lock.yaml` in its
`org.opencontainers.image.version` label, whatever its tag.

### Releasing

`sdk_version` in `components.yaml` is the only hand-edited copy of the
SDK version. `make lock` copies it into `sdk.lock.yaml` and
`build/sdk/pins.hcl`, and the `guard` job fails if either differs.
`make` passes it to `apptainer build` for the Apptainer image.

1. Set `sdk_version` in `components.yaml` to the release date,
   `YYYY.MM.DD`. Every component `ref:` must be a tag or a commit, not
   a branch, and `base_image` must be pinned by digest. On a release
   tag the `guard` job runs `scripts/check-lock.sh --release`, which
   fails otherwise; run it locally first.
2. Run `make lock`, and commit `components.yaml`, `sdk.lock.yaml` and
   `build/*/pins.hcl`.
3. Open a PR and merge it.
4. Tag the merge commit and push the tag:

   ```sh
   git tag openchip-v<version> <merge commit>
   git push github openchip-v<version>
   ```

   Creating a GitHub Release with the tag name `openchip-v<version>` on
   the merge commit does the same.

The `resolve` job fails before anything is pushed if the tag is not
`openchip-vYYYY.MM.DD`, or if it is not `openchip-v` followed by
`sdk_version` from `sdk.lock.yaml` at the tagged commit. To fix it,
delete the tag, bump `sdk_version` in `components.yaml`, run
`make lock`, merge, and tag the new merge commit.

### From-scratch verification

`workflow_dispatch` with **from-scratch** checked rebuilds both
components with no cache. These runs push the component images under
`<hash>-verify-<run id>` tags, so the reused `<hash>` images are not
replaced. They never publish an SDK image.
A failure means the pinned inputs no longer reproduce a build, for
example because a package mirror or a component commit has gone away.

The Apptainer publish job is disabled for now.

## Publishing from a feature branch

1. Open the repo on GitHub and go to the **Actions** tab.
2. In the left sidebar, click the **sdk** workflow.
3. Click the **Run workflow** button (top right of the run list).
4. In the dropdown, set **Use workflow from** to your feature branch.
   `main` works too.
5. Check the **publish** box ("Push the image to GHCR"). Leave the
   **from-scratch** box unchecked. It runs the no-cache verification
   described in [From-scratch verification](#from-scratch-verification),
   which takes hours and does not publish the SDK image.
6. Click the green **Run workflow** button to start it.

This triggers a new, separate run of `sdk` on that branch (distinct from
whatever run a plain `git push` already started) and pushes the image as
`ghcr.io/openchip-software/riscv-ime-sdk:openchip-v<short-sha>`, where
`<short-sha>` is the first 7 characters of the branch's current head
commit. It does **not** update the `:latest` tag, which only a release
tag moves. The run reuses the component images when their tags already
exist. Requires write access to the repo.
